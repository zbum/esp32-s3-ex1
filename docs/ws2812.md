# WS2812 가이드 (TinyGo + ESP32-S3)

이 보드의 온보드 RGB LED와 외부 WS2812/SK6812 스트립을 TinyGo로 구동하기 위한 가이드.

## 핀 / 전원

- 온보드 LED: **GPIO48** (보드에 "RGB" 표시)
- 외부 스트립: 임의 GPIO (출력 모드 설정 필요), 5V 전원, GND 공통
- 데이터 라인은 3.3V로도 대부분 동작하지만 길이가 길거나 픽셀 수가 많으면 레벨 시프터 권장
- 픽셀당 약 60mA(풀 화이트). 다수 픽셀이면 전용 5V 공급 필요

## 최소 예제

```go
package main

import (
    "image/color"
    "machine"
    "time"

    "esp32-s3-ex1/internal/ws2812"
)

const (
    ledPin     = machine.GPIO48
    numPixels  = 1
    brightness = 32
)

func main() {
    time.Sleep(2 * time.Second)
    ledPin.Configure(machine.PinConfig{Mode: machine.PinOutput})

    strip := ws2812.NewWS2812(ledPin)
    strip.SetBrightness(brightness)

    pixels := make([]color.RGBA, numPixels)
    palette := []color.RGBA{
        {R: 255, A: 255}, {G: 255, A: 255}, {B: 255, A: 255},
        {R: 255, G: 255, A: 255}, {G: 255, B: 255, A: 255},
        {R: 255, B: 255, A: 255}, {R: 255, G: 255, B: 255, A: 255},
    }

    for i := 0; ; i++ {
        c := palette[i%len(palette)]
        for j := range pixels {
            pixels[j] = c
        }
        if err := strip.WriteColors(pixels); err != nil {
            println("write err:", err.Error())
        }
        time.Sleep(500 * time.Millisecond)
    }
}
```

## 왜 `tinygo.org/x/drivers/ws2812`가 아니라 내부 패키지인가

업스트림 `tinygo.org/x/drivers/ws2812`는 `cortexm` / `tinygoriscv` 빌드만 생성한다(`gen-ws2812.go` 인자 참고). **Xtensa(ESP32 계열) 어셈블리가 없어서 ESP32-S3에서는 컴파일/동작이 불가**.

`internal/ws2812/`가 메우는 것:

- `ws2812_xtensa.go` — `//go:build xtensa`. 80 / 160 / 240MHz용 인라인 어셈블리 비트뱅 구현.
- `cpufreq_esp32s3.go` — `machine.GetCPUFrequency()` 결과로 어셈블리 분기 결정.
- `ws2812_init_other.go` — `!rp2040 && !rp2350`. 비트뱅 디바이스 생성.

## 240MHz 케이스: 왜 필요했는가

ESP32-S3는 부팅 시 기본 240MHz로 PLL 설정. 업스트림의 xtensa 패치 예제는 80/160MHz만 지원했다. 240MHz 상태에서 `WriteColors`를 호출하면 매번 `errUnknownClockSpeed`("ws2812: unknown CPU clock speed")가 반환되고 LED는 켜지지 않는다.

증상 확인용 진단 코드:

```go
if freq, err := machine.GetCPUFrequency(); err == nil {
    println("cpu freq:", freq)
}
if err := strip.WriteColors(pixels); err != nil {
    println("write err:", err.Error())
}
```

### 해결 옵션 비교

| 옵션 | 장점 | 단점 |
|------|------|------|
| 매 쓰기마다 160MHz로 토글 | 어셈블리 수정 불필요 | APB 클럭이 흔들려 UART/SPI/WiFi 타이밍 불안정 |
| 부팅 시 영구 160MHz | 단순 | WiFi(espradio) 등이 240MHz 가정이면 성능/안정성 저하 |
| **240MHz 어셈블리 케이스 추가** ✅ | CPU 240MHz 유지, 다른 페리페럴 영향 0 | 어셈블리 NOP 카운트 추가 |

이 프로젝트는 세 번째를 채택. `case 240e6:` 블록을 `internal/ws2812/ws2812_xtensa.go`의 switch에 추가했다.

### NOP 스케일링 근거

160MHz 블록의 NOP 수를 1.5배(240/160)로 늘리면 실제 ns 타이밍이 보존된다.

| 영역 | 160MHz NOPs | 240MHz NOPs | 결과 타이밍 |
|------|-------------|-------------|-------------|
| T0H 진입 (`s32i maskSet` 직후) | 37 | 56 | ≈250ns (스펙 220–380ns) |
| skip_store (T1H 연장) | 55 | 83 | T1H ≈596ns (스펙 580–1000ns) |
| 루프 꼬리 (T1L 연장) | 72 | 110 | T1L ≈471ns |

> WS2812 데이터시트의 T1L 최소 580ns보다 짧지만, 160MHz 케이스가 같은 비율로 짧고 실측에서 안정 동작한다. 일부 클론 칩(특히 SK6812)에서 색이 깜빡이면 마지막 영역의 NOP을 +20 정도 추가.

## SK6812(RGBW) 사용

```go
strip := ws2812.NewSK6812(ledPin)   // GRBW, color.A를 white 채널로 사용
```

## 운영 팁

- `SetBrightness(0)`로 끄면 픽셀 데이터는 보내지만 모두 0이 됨. 완전 차단하려면 데이터 송출 자체를 멈춘다.
- 인터럽트는 `WriteByte` 내부에서 비활성화됨. WiFi가 가끔 픽셀을 글리치하면 호출 빈도를 낮추거나 RMT 페리페럴 기반 드라이버로 이전 검토.
- 갱신 주기는 `TRES > 50µs` 보장. `time.Sleep(time.Microsecond * 100)` 이상이면 안전.
